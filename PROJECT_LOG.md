## A. Project overview
- **Title:** AI-Powered Resume Screening and Job Matching System Using Natural Language Processing
- **Problem statement:** Recruiters read many resumes against one job description. This is slow and inconsistent. The project ranks resumes against a job description and explains each ranking, to support (not replace) human review.
- **Objectives:** (1) extract text from PDF resumes; (2) extract skills with a transparent dictionary; (3) score with TF-IDF, with a pretrained Sentence Transformer, and with a combined score; (4) compare the three methods on a labeled evaluation set; (5) present it in a Streamlit app.
- **Scope:** Individual project, no model training or fine-tuning, no LLM, no database, no GPU.
- **Motivation / related work / references:** motivation as above. Verified references so far (Phase 11): Reimers and Gurevych, Sentence-BERT, EMNLP-IJCNLP 2019 (https://aclanthology.org/D19-1410); Wang et al., MiniLM, arXiv:2002.10957; scikit-learn TF-IDF documentation. A fuller related-work section is still PENDING (Phase 12).

### Verified model facts (measured by loading the model on this machine)
- Model: `sentence-transformers/all-MiniLM-L6-v2`, pretrained, not trained or fine-tuned by us.
- `max_seq_length` = **256** word-piece tokens (including the 2 special tokens).
- Embedding dimension = 384. Pipeline modules: Transformer, Pooling, Normalize (outputs are unit length, so cosine = dot product).
- Truncation confirmed empirically: a 1000-word input (1002 tokens) gives the same embedding as its first 254 words. Everything beyond the limit is silently ignored. A one- or two-page resume will exceed this, so chunking is required (below).

### Combined score: method (fixed before any evaluation)
Final score for candidate *i* against a job description:

`Combined_i = 0.50 * S_i + 0.20 * T_i + 0.30 * K_i`

Weights are fixed at 0.50 / 0.20 / 0.30 as initial experimental weights. They are not optimal and **will not be tuned on the evaluation set** (see below).

Each component is a deterministic function of that one resume and the job description only. It does not depend on the other resumes in the upload or on the session.

| Component | Definition | Range | Notes |
|---|---|---|---|
| K (skill coverage) | `\|required skills found in resume\| / \|required skills in JD\|` | [0, 1] | Has a direct meaning (fraction). If the JD has no extracted required skills, K is undefined: it is excluded, the other weights are renormalised (0.50/0.70, 0.20/0.70), and the UI flags this. |
| T (TF-IDF) | cosine of L2-normalised TF-IDF vectors | [0, 1] | TF-IDF weights are non-negative, so cosine cannot be negative. The vectorizer is fitted once on a fixed reference corpus (not on the uploaded batch), so IDF values do not change with whatever the recruiter uploads. Exact corpus decided in Phase 5. |
| S (semantic) | `max(0, cosine_aggregated)`, aggregation below | [0, 1] | MiniLM cosine can be negative. Negative cosine means "dissimilar", so it is mapped to 0 match. Values are never multiplied by 100 and presented as a percentage. |

What was rejected, and why:
- **Min-max or z-score across the uploaded batch:** rejected. The same resume would get a different score depending on which other resumes were uploaded, so results would not be reproducible, and with one resume the formula is undefined.
- **Assuming the three [0,1] scores are comparable:** not assumed. A cosine of 0.5 from MiniLM and 0.5 from TF-IDF mean different things, and their typical spreads differ. In a weighted sum the effective influence of a component is roughly `weight x spread of that component across candidates`, not the weight alone. We will therefore **report each component's observed mean and standard deviation** as a diagnostic in EXPERIMENT_RESULTS.md. This is for interpretation only, not for retuning.
- **Optional, pre-specified extension (not the main result):** fixed anchored rescaling `clip((x - lo) / (hi - lo), 0, 1)` per component, where `lo` and `hi` are constants measured once on a separate calibration set (for example unrelated pairs for `lo`, near-duplicate pairs for `hi`). They would be frozen and recorded before running the evaluation set. The default is `lo = 0, hi = 1` (no rescaling). If run, it is reported as a separate row, clearly marked exploratory.

The result is a **matching index** that supports ranking. It is not a probability of job success and not a percentage of qualification.

### Weight handling and avoiding evaluation leakage
- The main reported result for Method C uses the fixed 0.50 / 0.20 / 0.30 weights, run once.
- Any weight sensitivity analysis (e.g. trying 0.4/0.3/0.3 or equal weights) is reported in a **separate, labelled exploratory table**. These are used to discuss how rankings respond, never to pick new weights and then report the same data as unbiased performance.
- If weights are ever re-chosen, they must be chosen on a development set of job descriptions and reported on a disjoint test set. With the planned ~5 job descriptions this likely will not be possible, which is a limitation we will state.

### Chunking for the Sentence Transformer (decided in Phase 2, implemented in Phase 6)
Problem: the model reads only the first 256 tokens, so a long resume would be scored on its opening lines only, and the skills section is often near the end.

Strategy:
1. Use the model's own tokenizer to count tokens (word-pieces, not words).
2. Split text on line and sentence boundaries, then pack consecutive pieces greedily into chunks of at most **200 tokens**. This leaves a margin below the 254 usable tokens. A single piece longer than 200 tokens is hard-split by tokens.
3. Overlap: carry roughly the last 40 tokens of the previous chunk into the next, so a sentence at a boundary is not lost.
4. Apply the same chunking to the job description. A JD of 200 tokens or fewer is a single chunk.
5. Encode all chunks in one batch. Encoding happens once per document.

Aggregation (job description chunks `J_1..J_m`, resume chunks `R_1..R_n`):

`cos_agg = sum_i (w_i * max_j cos(J_i, R_j)) / sum_i w_i`, where `w_i` is the token length of `J_i`.

Meaning: for every part of the job description, find the best-matching part of the resume, then take the length-weighted average. This asks "is each requirement area covered somewhere in the resume?" and avoids two failure modes:
- *Mean-pooling all resume chunks into one vector* dilutes a strong skills section with irrelevant sections such as education or hobbies.
- *Taking the single max over all pairs* lets one lucky chunk decide the score.

Known weaknesses (to be discussed with measured examples): `max` rewards one strongly matching chunk even if other requirement areas are missing, and the score depends on how the chunks happened to be split. Chunk size, overlap and aggregation are fixed now and will not be changed after seeing evaluation results. An ablation using the mean-pooled alternative may be reported as an exploratory row only.

### PDF parsing (Phase 3, `src/pdf_parser.py`)
- **Library/API:** PyMuPDF (`import pymupdf`). Text is read per page with `page.get_text("blocks", sort=True)`: blocks come in reading order (top to bottom, then left to right). Lines inside a block keep their `\n`; blocks are joined by a blank line; pages are joined by a blank line.
- **Light cleanup only:** remove NUL characters, normalise newlines, strip trailing spaces, collapse 3+ newlines to 2. Real preprocessing (case, punctuation, technical terms) is deliberately left to Phase 4. This output is the "original extracted text" kept for evidence.
- **In memory only:** the parser takes `bytes` and never writes to disk, so uploads are not stored. (`extract_text_from_path` exists for scripts and tests and only reads.)
- **Every file gets an `ExtractionResult`** with `status`, a human-readable `message`, `warnings`, `page_count`, `char_count` (non-whitespace), SHA-256 `content_hash`. `result.usable` is True only for status `ok` / `ok_with_warnings` with non-blank text. A failure is never returned as an empty resume.
- **Statuses:** `ok`, `ok_with_warnings`, `scanned_likely`, `no_text`, `encrypted`, `corrupted`, `empty_file`, `too_large`, `extraction_failed`.
- **Scanned-PDF heuristic (a guess, not proof):** if total non-whitespace characters < `MIN_TOTAL_CHARS` (100) and at least one page has an image and fewer than `MIN_CHARS_FOR_TEXT_PAGE` (20) characters, status = `scanned_likely` and the message says OCR is required. If a text PDF has some image-only pages, it stays usable with a warning that those pages were not read. OCR itself is optional and not implemented.
- **Other limits:** files > 10 MB are refused (`MAX_FILE_BYTES`). A PDF that PyMuPDF had to repair gets a warning. One bad file never stops a batch.
- **Duplicates:** `make_unique_ids` turns repeated filenames into `cv.pdf`, `cv (2).pdf`, ... (both kept, collision-safe). Identical content (same SHA-256) under any filename sets `duplicate_of` on the later file, so the caller can exclude it from ranking. Zero-byte files are not hash-matched as duplicates.
- **Threshold values are initial choices** and are not tuned on any dataset.

### Preprocessing (Phase 4, `src/preprocessing.py`)
One shared `normalize_text` (Unicode NFKC, curly quotes/long dashes to ASCII, zero-width and soft-hyphen removal, bullet glyphs including Word's private-use bullet to "- ", hyphen-at-line-break joined *keeping* the hyphen, whitespace collapsed, case untouched), plus `remove_contact_info` (e-mails, URLs, phone numbers with at least 9 digits so "2019 - 2023" survives). Then three views:

| | skills | TF-IDF | embeddings |
|---|---|---|---|
| function | `preprocess_for_skills` | `tfidf_tokens` / `preprocess_for_tfidf` | `preprocess_for_embeddings` |
| case | kept | lowercased | kept |
| punctuation | kept | kept inside tokens (`c++`, `c#`, `.net`, `node.js`, `ci/cd`, `scikit-learn`) | kept |
| stop words | kept | removed, except `front`, `back`, `full`, `system` | kept |
| contact info | removed | removed | removed |
| line breaks | kept | n/a (tokens) | kept (Phase 6 chunker splits on lines) |

- **TF-IDF tokenization:** regex token = letters/digits optionally joined by `.` `-` `/`, optionally ending in `++`, `+` or `#`; `.net` is its own token. Numeric-only tokens and single letters other than `c` and `r` are dropped. Aliases are **not** merged ("sklearn" and "scikit-learn" stay different tokens), because TF-IDF is the traditional baseline and alias normalisation is the skill extractor's job. Phase 5 must use `TfidfVectorizer(lowercase=False, token_pattern=r"\S+")` on this output, otherwise sklearn's default pattern cuts `c++` to `c`.
- **Measured fact:** sklearn's English stop-word list (318 words) contains `front`, `back`, `full` and `system`, so a default vectorizer would delete "front end", "back end", "full stack" and "system design". A test asserts the keep-list works.
- **Evidence text:** skill evidence is a snippet of the skills view (whitespace/Unicode cleaned, contact info removed). The untouched original stays in `ExtractionResult.text`.
- **Deliberate removal of contact info from the embedding view:** the only non-cosmetic deletion there; justified by the 256-token window and by keeping personal details out of the ranking.

### Skill extraction (Phase 4, `src/skill_extractor.py` + `data/skill_dictionary.json`)
- **What it is:** a rule-based phrase matcher over a hand-written dictionary. It is **not** a trained NER model: it only finds listed skills, cannot judge level or negation ("no Python experience" still matches Python), and cannot see unlisted skills.
- **Dictionary:** 114 skill entries (counted by loading the file) in JSON: languages, databases, web frameworks, ML/NLP/data tools, cloud/DevOps, tools/testing, practices. Each entry has `name` (canonical form used for comparison), `category`, `aliases`, optional `rules`. The 23 skills named in the project brief are asserted present by a test.
- **Matching:** each alias is a regex that may not touch a letter/digit on either side and may not follow a `.`. This blocks SQL in MySQL/NoSQL, Java in JavaScript, Git in GitHub/digital, .NET in ASP.NET, js in Node.js, R in R&D. Space and hyphen in an alias are interchangeable, so "machine learning" matches "machine-learning" and a line break between the words. Overlaps: the longest match wins (Microsoft SQL Server beats SQL, C++ beats C).
- **Ambiguous words** (Go, R, C, React, Express, Spark, Excel, Oracle, Swift, Ruby, JS, TS...) carry rules: exact capitalisation and/or a context word in the *same sentence* and within 80 characters. The same-sentence limit was added after a probe on a one-line text showed a context word in a neighbouring sentence "vouching" for `React` and `JS`.
- **Output:** each skill gives canonical name, category, count, the distinct wordings found (e.g. `sklearn`), and up to 3 evidence snippets (the containing line, or +-70 characters if the line exceeds 160). Each match also has start/end offsets.
- **Job descriptions:** `extract_job_skills` splits skills into required and preferred using visible rules: headings like "Nice to have:" / "Preferred" switch to preferred, "Requirements:" / "Skills:" switch back; an inline cue ("a plus", "bonus", "nice to have") affects only its own sentence; a skill appearing in both counts as required; a JD with no structure is all required. Bullet lines are never treated as headings. (A first version applied an inline cue to the whole line, which demoted every skill in a one-paragraph JD; found by a test, fixed, regression test added.)
- **How to add a skill later:** open `data/skill_dictionary.json` and add `{"name": "Rust", "category": "Programming Language", "aliases": ["rustlang"]}` to the `skills` list. If the word is also ordinary English, add `"rules": {"Rust": {"case_sensitive": true, "context": ["cargo", "programming"]}}` (rule key = the exact name or alias it applies to). No code changes needed. Loading raises an error if two skills share an alias, a name is duplicated, or a rule key is not a name/alias of its skill.
- **Not done on purpose:** required-skill coverage (matched / missing and the fraction) is part of scoring and comes in Phase 7.

### TF-IDF baseline, Method A (Phase 5, `src/tfidf_matcher.py`)
- **What it is:** traditional NLP only: `TfidfVectorizer` + cosine similarity. No embeddings, no LLM, no skill coverage, no classifier. Fitting learns the **vocabulary** and the **inverse document frequency** of each term by counting documents. It is not neural-network training: no gradients, epochs or labels.
- **Formulas (scikit-learn with the settings below):** `tf = 1 + ln(count)`; `idf = ln((1 + n) / (1 + df)) + 1`; weight = tf x idf; each document vector is scaled to unit length; `cosine = a . b` for unit vectors. All weights are non-negative so the score is in [0, 1].
- **Score meaning:** a text-overlap score. It is not a probability, not a percentage and not a chance of getting hired; 0.8 does not mean "80% match". Only the ordering and relative sizes are informative, and only under the same fit mode.
- **Preprocessing:** reuses `preprocess_for_tfidf` from Phase 4 (no duplicated logic). Output is whitespace-separated tokens, so the vectorizer must be `lowercase=False, token_pattern=r"\S+"`. Tests prove `c++`, `c#`, `.net`, `node.js`, `ci/cd`, `scikit-learn` are single vocabulary entries and that sklearn's defaults would have split them (`node` + `js`) or dropped them (`c++`, `.net`).
- **Vectorizer configuration (`make_vectorizer`):** `lowercase=False`, `token_pattern=r"\S+"`, `ngram_range=(1, 2)`, `sublinear_tf=True`, `use_idf=True`, `smooth_idf=True`, `norm="l2"`, `min_df=1`, `max_df=1.0`. Rationale: bigrams capture "machine learning"; sublinear tf limits keyword stuffing; no document-frequency pruning because pruning with a handful of documents removes real terms. **These are fixed design choices, not tuned on any evaluation data.**
- **Interface:** `rank_resumes(jd, candidates, reference_texts=None)` or `TfidfMatcher().rank(jd, candidates)`. `candidates` is `{id: text}` or `[(id, text), ...]`. Returns a `TfidfRanking` with one `TfidfScore` per candidate (id, raw cosine, rank, token count, top contributing terms), sorted best first; ties keep input order and share a rank (1, 1, 3). The contributions of all shared terms add up exactly to the score (tested for a small case); the 5 largest are stored for explanation.
- **Two fit modes, recorded in `fit_scope`:**
  - `batch` (default): vectorizer fitted on the job description + the *unique* resumes of this call (identical resumes counted once, so a duplicate cannot shift others' scores). Fresh vectorizer per call, no state kept. Limitation (tested): IDF depends on which resumes are in the batch, so a resume's score can change with its companions.
  - `reference`: `TfidfMatcher().fit(reference_texts)` once; IDF then comes from that fixed corpus and is the same for every call (tested). Terms outside the reference vocabulary are ignored, with a warning if no job-description term is known.
  - **Change from the Phase 2 plan:** Phase 2 said TF-IDF would be fitted on a fixed reference corpus. No reference corpus exists, so both modes are implemented. **Resolved in Phase 7: the ranker, the Phase 8 evaluation and the Phase 9 app all use the pairwise scope (IDF fitted on the job description and that one resume); the reference mode exists but is not used anywhere.** With only 2 to 3 documents, IDF is nearly flat, so batch-mode TF-IDF behaves close to plain term-frequency cosine.
- **Edge cases:** job description empty / only stop words / punctuation / numbers -> `ValueError("... no usable terms ...")`. Non-string job description or text, candidates given as a string or non-pairs, non-string ids -> `TypeError`. Duplicate candidate ids -> `ValueError`. Empty candidate collection -> empty ranking, no error. Empty / stop-word-only / punctuation-only resume -> score 0.0, `token_count` 0, and a warning naming the id. Zero overlap -> exactly 0.0. Identical text -> equal scores and shared rank. Unusable reference corpus -> `ValueError`.
- **Phase 4 change made in Phase 5 (genuine defect):** `go` is in sklearn's English stop list, so the Go language disappeared from the TF-IDF view. It was found when the demo output was checked. `go` was added to `TFIDF_KEEP_WORDS` with a regression test. Cost: the ordinary verb "go" now also becomes a token; IDF down-weights it. Other stop-list words that can matter in technical text (`get`, `put`, `call`, `next`) were left removed; this is a known small loss.
- **Commands:** `python -m pytest tests/test_tfidf_matcher.py -v` (this component), `python -m pytest -q` (everything), `python -m src.tfidf_matcher` (prints a labelled synthetic demo).

### Semantic matching, Method B (Phase 6, `src/semantic_matcher.py`, `src/inputs.py`)
- **Model:** pretrained `sentence-transformers/all-MiniLM-L6-v2`, used as published (not trained or fine-tuned by us), CPU by default, no GPU needed. Measured: `max_seq_length` 256 (254 usable after `[CLS]`/`[SEP]`), embedding dimension 384, output already unit length. Loaded lazily, once, through `get_model()`; the matcher object is meant to be created once and reused (Streamlit will wrap it in `st.cache_resource` in Phase 9). Load or encode failures raise `SemanticModelError` with a plain explanation (first run needs the internet to download about 90 MB; afterwards it reads the local cache).
- **Preprocessing:** `preprocess_for_embeddings` from Phase 4 (no duplicated logic), applied to the job description and to every resume before chunking.
- **Chunking** (parameters fixed in Phase 2, unchanged): (1) text of at most 254 tokens stays ONE chunk (short documents are never split); (2) otherwise cut into units: lines, then sentences for an over-long line, then words, then halved characters for an unbroken giant word; (3) pack units greedily into chunks of at most **200 tokens** (safety margin under 254); (4) overlap = the last whole units of the previous chunk that fit in **40 tokens** (so overlap is at most 40 tokens, sometimes less or none when the last line is longer than 40); (5) token counts come from the model's own tokenizer, without special tokens, and add up exactly over whitespace-separated units, which a test confirms against a real recount; (6) every `Chunk` is an exact slice of the preprocessed document with `doc_id`, `index`, `start`, `end`, so it can be traced and shown as evidence. A safety recount warns if any chunk would still be truncated (none occurred in tests). Chunking limits information loss; it does not give the model an understanding of the whole document, and meaning that spans two chunks is not captured.
- **Aggregation** (pre-registered in Phase 2, unchanged): for each job-description chunk take its best cosine against the resume chunks, then average over job-description chunks weighted by their token counts: `score = sum(w_i * best_i) / sum(w_i)`. `top_k=1` (the maximum) is the default; `top_k>1` (mean of the k best resume chunks) exists for exploratory comparison only. Verified against hand-computed values (1/3, 1.0, 0.7333, 2/3, 0.5).
  - **Trade-off stated plainly:** the maximum keeps a strong skills section from being diluted by education or hobby sections. But a single resume chunk decides each `best_i`, and a job description that fits in one chunk (the usual case) means one resume chunk decides the whole score. Weighting across job-description chunks limits the influence of one chunk only for long job descriptions. The best-matching resume chunk is kept in `best_matches` so a person can read what was matched. I did not change the pre-registered method; whether `top_k=2` is better is a question for an exploratory table in Phase 8, not a setting to pick after seeing results.
- **Output:** raw aggregated cosine in [-1, 1] (no clipping or rescaling here; Phase 7 applies `max(0, .)`). It is not a probability or percentage and is not on the same scale as the TF-IDF cosine. Observed in the demo: even a pastry-chef resume scored +0.13 against a machine-learning job description while its TF-IDF score would be 0, so the two scores cannot be added as if they meant the same thing; Phase 7 must examine both distributions.
- **Ranking rules:** descending score; equal scores (12 decimals) share a rank and keep input order (deterministic); blank resumes get `empty=True`, score 0.0, and are always ranked **last** (otherwise a blank 0.0 would beat a genuinely dissimilar resume scoring below 0). Identical chunk texts are embedded once per call, all in one batched `encode` call (batch size 32).
- **Errors:** non-string job description or text, bad candidate containers/items -> `TypeError`; blank job description, duplicate candidate ids, invalid configuration (for example `chunk_tokens` above 254, overlap not smaller than chunk size, `top_k` < 1) -> `ValueError`; an empty candidate collection returns an empty ranking.
- **Refactor:** the candidate validation moved from `tfidf_matcher.py` to the shared `src/inputs.py` (identical behaviour; all Phase 5 tests still passed unchanged right after).
- **Defect found by my own test and fixed:** `get_model` was decorated directly with `lru_cache`, so `get_model()`, `get_model(MODEL_NAME)` and `get_model(MODEL_NAME, "cpu")` were three cache keys and would have loaded the model up to three times. It is now a thin wrapper over a cached loader; a regression test asserts the three spellings return the same object.
- **Commands:** `python -m pytest tests/test_semantic_matcher.py -v`, `python -m pytest -q`, `python -m src.semantic_matcher` (labelled synthetic demo with the real model).

### Combined scoring and ranking, Method C (Phase 7, `src/ranker.py`)
- **Architecture:** `pdf_parser` -> `ExtractionResult` -> `CandidateRanker` which calls `preprocess_for_skills` + `SkillExtractor` (job description: `extract_job_skills`; resume: `extract`), `TfidfMatcher` and `SemanticMatcher`, then `combine_scores`. Output is a `RankingReport` with one `CandidateResult` per candidate, the `JobAnalysis`, the excluded files, the configured weights, the TF-IDF scope and the model name. `rank(jd, candidates)` takes `{id: text}`; `rank_extractions(jd, extract_many(...))` takes parser output and lists unusable or duplicate files in `excluded` with the reason ("needs a manual look"), so nobody is dropped silently or rejected automatically. `report.to_records()` gives flat rows for a table or CSV.
- **Formula (fixed, configurable through `ScoringConfig`, weights must sum to 1):**
  `index = 0.50 * S + 0.20 * T + 0.30 * K` with `S = max(0, raw semantic cosine)`, `T = raw TF-IDF cosine`, `K = |matched required skills| / |required skills|`. The weights are initial design choices, not optimal, and were not tuned on any labels.
- **Score distributions inspected first** (10 SYNTHETIC resumes incl. blank, stop-word-only and gibberish; observations, not evaluation):
  - Semantic cosine ranged from +0.008 to +0.763 (mean 0.32, sd 0.21) among non-empty texts; TF-IDF (pairwise) from 0.000 to 0.213 (mean 0.043, sd 0.068). Semantic scores spread about 3x wider, and an unrelated pastry-chef resume still got +0.18 semantic against exactly 0.0 TF-IDF.
  - **Semantic cosine can be negative**: short unrelated strings gave -0.026 ("the cat sat on the mat") and -0.023 (punctuation only); resume-like texts in this set were never negative. `max(0, cosine)` therefore rarely changes anything, but it is applied, flagged (`semantic_clipped`) and the raw value is always kept.
  - The semantic model ignores negation: "no experience with Python or SQL whatsoever" scored +0.376 against the backend job description, above a restaurant resume. Skill coverage (a dictionary match) shares this blind spot.
  - Blank resume: semantic marked empty (0.0), TF-IDF 0.0. Zero-overlap resume: TF-IDF exactly 0.0.
  - Consequence for the weights: a component's real influence is roughly weight x spread, so the nominal 20% TF-IDF weight acts closer to a few percent next to the semantic term. This is documented as a property of the baseline, **not corrected**; correcting it would need a separate calibration set (the optional anchored rescale from Phase 2 is not used).
- **Transformations applied:** only `max(0, .)` on the semantic cosine, plus renormalising weights when a component is unavailable. Nothing is rescaled, nothing depends on other candidates. Out-of-range or non-finite inputs to `combine_scores` raise `ValueError` instead of being silently clipped (only 1e-9 float noise is tolerated).
- **TF-IDF scope (decision):** Phase 5's `batch` mode fails the requirement that a candidate's score not change when an unrelated candidate is added (measured: the same resume scored 0.2553 in a batch of 10 and 0.2134 alone). The ranker therefore fits TF-IDF **per (job description, one resume) pair** (`tfidf_scope="pairwise"`), which makes each score a function of that pair only. The price: with two documents IDF is nearly flat, so TF-IDF behaves close to plain term-frequency cosine. If a `TfidfMatcher` fitted on a reference corpus is passed in, scope is `"reference"` (fixed IDF, also batch-independent). Resolved: Phase 8 and the Phase 9 app use `pairwise`; the reference mode is implemented and tested but not used anywhere.
- **Required-skill coverage:** unique canonical skills only (aliases map to one name, so `sklearn` = `scikit-learn`; repeated mentions in the resume or job description count once). Required skills come from `extract_job_skills`; preferred skills are reported (`matched_preferred`, `missing_preferred`) but never enter K.
- **Missing or ambiguous skill information:**
  - No required skills (none found, or all appear only in preferred parts): K is `None`, never 1.0. The index uses S and T with weights renormalised (0.50/0.70, 0.20/0.70); each candidate carries a warning and the report carries one saying such an index is not comparable with one from a job description that has required skills.
  - No heading or cue phrase in the job description: all identified skills default to required and `split_uncertain=True` with a warning. To support this, `JobSkills` gained a `structured` flag (a Phase 4 change; regression test added).
  - No skills at all in the job description: stated in a warning.
  - A resume with zero dictionary skills gets a warning that this may reflect layout, wording or dictionary gaps.
  - Job description with no usable TF-IDF terms: T is left out and weights renormalised, with a warning.
- **Ranking rules:** best index first; ties (12 decimals) share a rank and keep input order; resumes with no usable text are flagged `empty` and always ranked after non-empty ones (a test makes both score exactly 0.0 to prove the order does not come from the number).
- **Index vs probability:** the index orders candidates for human review. It is not a probability of being hired or qualified, and not a validated percentage match; a value like 0.70 has no calibrated meaning.
- **Commands:** `python -m pytest tests/test_ranker.py -v`, `python -m pytest -q`, `python -m src.ranker` (labelled synthetic demo).

### Phase 8 evaluation protocol (written BEFORE the dataset was created and before any ranking was inspected)
**Question:** on a small, hand-built SYNTHETIC set, how well do (A) TF-IDF alone, (B) semantic similarity alone and (C) the combined index order candidates compared with written relevance judgments?

**Fixed methods (nothing below may be changed after the labels or any ranking have been looked at):**
- **A. TF-IDF:** raw cosine from the existing pairwise configuration (`TfidfMatcher`, vectorizer from `make_vectorizer()`: `lowercase=False`, `token_pattern=\S+`, `ngram_range=(1,2)`, `sublinear_tf=True`, `min_df=1`, `max_df=1.0`, smooth idf, L2 norm; IDF fitted on {job description, that one resume}).
- **B. Semantic:** raw aggregated cosine from `SemanticMatcher` with `sentence-transformers/all-MiniLM-L6-v2`, CPU, `chunk_tokens=200`, `overlap_tokens=40`, `top_k=1`, batch size 32, JD-chunk-weighted mean of best resume-chunk cosine. Ranked by the RAW cosine (negative values are not clipped for ranking B).
- **C. Combined:** `CandidateRanker` with `ScoringConfig(0.50, 0.20, 0.30)`: `index = 0.50*max(0,S) + 0.20*T + 0.30*K`. Skill dictionary `data/skill_dictionary.json` frozen as it is now (its SHA-256 is recorded in `artifacts/evaluation_config.json`).
- All three are read from ONE `CandidateRanker.rank()` call per job (raw `tfidf_similarity`, raw `semantic_similarity`, `combined_index`), so no matcher logic is duplicated in the evaluation code and all methods see exactly the same inputs.

**Data:** 5 synthetic job descriptions (backend, frontend, data analyst, machine-learning, full-stack), 9 to 10 synthetic resumes each. Stored in `data/evaluation/dataset.json` (jobs, resumes) and `data/evaluation/labels.csv` (graded labels with rationale), rubric in `data/evaluation/RUBRIC.md`. Labels are written from the rubric and the resume text only, then reviewed once and **frozen before any method is run**; the SHA-256 of the dataset and labels is recorded. Labels are not changed after seeing results.

**Relevance and metrics (K = 3):**
- Binary relevance for Precision/Recall/MRR: label >= 2 is relevant. Graded labels 0-3 for nDCG.
- `Precision@3 = (relevant in top 3) / 3` (if a pool had fewer than 3 candidates the missing slots count as non-relevant). `Recall@3 = (relevant in top 3) / (all relevant in the job's pool)` (can be below 1 even for a perfect ranking when a pool has more than 3 relevant candidates).
- `MRR = 1 / rank of the first relevant candidate` (0 if none is relevant among those ranked).
- `nDCG@3 = DCG@3 / IDCG@3`, `DCG@3 = sum over positions i=1..3 of (2^label_i - 1) / log2(i + 1)`, IDCG from the best three labels in that job's pool.
- If a job has no relevant candidate (or all labels 0) the metric is undefined for that job: it is excluded from the average and flagged (not silently scored 0).
- **Aggregate = macro average over jobs** (each job counts equally).
- **Ties:** the candidate order given to the ranker is fixed and label-independent (sorted by SHA-256 of the candidate id, so ids do not favour any profile type); equal scores (12 decimals) keep that order. As a sensitivity check the metrics are also computed with best-case and worst-case tie-breaking (ties ordered by label), reported separately as bounds.
- **Reporting:** per-job and macro metrics for A, B, C; raw component scores saved; configuration saved. No significance claims (5 jobs, about 46 judgments).

**Dataset created and frozen (2026-10-24), before any matcher was run on it:**
- 5 jobs, 46 resumes (JD-BE 9, JD-FE 9, JD-DA 10, JD-ML 9, JD-FS 9) = 46 judgments. Label counts per job as (label 3 / 2 / 1 / 0): BE 3/2/2/2, FE 2/2/3/2, DA 3/2/3/2, ML 2/2/3/2, FS 3/2/2/2; relevant (label >= 2) per job: BE 5, FE 4, DA 5, ML 4, FS 5. Profile types: strong match, strong match with alias wording, relevant paraphrase without named tools, partial match, adjacent role, keyword list without evidence, negation, "describes the role from outside" (recruiter, designer, product manager, technical writer), sparse/ambiguous, long resume with the relevant part at the end, unrelated-with-overlap. Strong candidates deliberately do NOT all reuse the job description's words, and weak ones deliberately reuse its vocabulary.
- Labels were written from `RUBRIC.md` and the text only, reviewed once against the rubric (no changes), then frozen. SHA-256 at freeze time: `dataset.json` 1e8aa786...79ae, `labels.csv` 97f3db54...e3d7, `RUBRIC.md` 0d2ae989...a6d, `skill_annotations.json` 709ee0c7...cf0, `skill_dictionary.json` 4220dd17...0f1 (full hashes are written to `artifacts/evaluation_config.json` by the evaluation script).
- Quality check of the data (not of rankings): only 2 resumes exceed the model's 254-token limit (BE-09: 295 tokens, 2 chunks; DA-09: 282 tokens, 2 chunks); FS-09 is long-ish but fits in one chunk, so only 2 of the "long, relevant at the end" cases actually exercise chunking. Longest short resume: 232 tokens.
- Check of the JOB DESCRIPTIONS only (what the frozen skill extractor reads as required/preferred). All five are detected as structured. Required sets: BE {Python, SQL, PostgreSQL, Docker, REST API}; FE {JavaScript, React, HTML, CSS, REST API, Git}; DA {SQL, Excel, Tableau, Data Visualization}; ML {Machine Learning, Python, Deep Learning, PyTorch, TensorFlow, NLP}; **FS {JavaScript, Node.js, Express.js, MongoDB}: React is NOT detected**, because the rule for the ambiguous word "React" needs a context word in the same sentence and "React for the user interface" has none. I left the job description and the dictionary unchanged (the dictionary is frozen by this protocol) and will report this as a limitation affecting method C on JD-FS. Also, JD-ML requires both PyTorch and TensorFlow in coverage although the text says "PyTorch or TensorFlow"; the extractor cannot represent "or".
- Skill-extraction annotations: 17 resumes annotated by hand before running the extractor (`skill_annotations.json`, mention-level, dictionary vocabulary only, one annotator who also wrote the dictionary).

**Exploratory analyses (reported separately and never used to choose settings):** ablations computed from the stored raw components (skills alone, semantic+TF-IDF without skills, other weightings). They do not alter the main result.

**Known threats to validity (stated in advance):** the same person (the project author, with an AI assistant) wrote the system, the resumes and the labels, and knows the system's weaknesses, so the dataset may be harder or easier for it than independent data would be; the data are synthetic and say nothing about real hiring; labels are subjective; 5 jobs is far too few for strong conclusions.

### Streamlit application (Phase 9: `app.py`, `src/app_logic.py`, `.streamlit/config.toml`)
- **Run:** from the project folder with the virtual environment active: `streamlit run app.py` (opens http://localhost:8501). The server is restricted to `localhost` by `.streamlit/config.toml` (also `maxUploadSize = 25` MB per file and usage statistics off). The first semantic or combined run loads the model (about a minute on this machine); later runs reuse it.
- **Architecture:** `app.py` is only the interface. `src/app_logic.py` (no Streamlit import, unit-testable) orchestrates the existing modules and builds rows, the table and the CSV: parser `extract_many` -> `partition_extractions` (small public helper moved out of `CandidateRanker.rank_extractions`, behaviour unchanged) -> one of three existing APIs. **No matching algorithm was added or changed**: *combined* = `CandidateRanker.rank` (Phase 7 formula and 0.50 / 0.20 / 0.30 weights untouched); *TF-IDF* = `TfidfMatcher.rank` called per resume, i.e. the pairwise IDF used in the evaluation; *semantic* = `SemanticMatcher.rank` (chunk 200 / overlap 40 / top_k 1). Only the app layer sorts the TF-IDF rows (best first, ties keep input order and share a rank, resumes with no usable words last), the same rules the other two use.
- **Interface:** sidebar with method choice (combined is the default) and a synthetic demo (scenario picker, "fill in this job description", ZIP of that scenario's synthetic resumes as PDFs with neutral file names and no labels). Main page: 1 job description with detected required / preferred skills and warnings (uncertain split, no skills); 2 resumes with an extraction-status table (readable, scanned, no text, password-protected, corrupted, empty, too large, duplicate, with the reason and "needs a manual look") and an extracted-text check; 3 "Rank candidates" button; 4 results: sortable table with only the columns the chosen method calculated (labels: Combined matching index, Semantic similarity (raw cosine), TF-IDF similarity (cosine), Required-skill coverage, Required skills matched n/m), CSV download, one expander per candidate (matched / missing required skills, matched preferred skills, skill evidence snippets, best-matching passage or top shared TF-IDF terms, candidate warnings), and a "Files not ranked" table. A banner says results are stale when the inputs changed after ranking.
- **Wording rules kept:** scores are never called probabilities or percentages; a visible notice says the tool is decision support, scores reflect text matching and dictionary matches, the synthetic evaluation (combined better than TF-IDF, not clearly better than semantic alone) does not establish real-world performance, and users need permission to process the resumes. Nobody is rejected automatically; excluded files are listed with the reason.
- **Validation and errors:** empty job description, no uploads, TF-IDF with a job description of only stop words / numbers each give a plain message (and `match()` raises `ValueError` if called with such inputs). One bad PDF never stops the others. Only `SemanticModelError` (model cannot load, e.g. offline on first run) is turned into a friendly message; any other exception is deliberately NOT caught so real bugs stay visible (a test asserts this).
- **Caching:** `st.cache_resource` holds one `CandidateRanker`, so one loaded model per server process (the model itself is also cached in `get_model`). `st.cache_data` (per browser session, at most 8 entries, 1 hour) caches PDF extraction and matching. Keys are the actual content: file names and bytes, job description text, method and a configuration signature (weights, model name, chunk settings, TF-IDF scope); the ranker object is excluded from hashing. Tests prove identical inputs are not recomputed, while a changed job description, a changed resume (same name, new content) or a different method is recomputed with the new content, and that the ranker is built once. "Clear cached data now" empties the caches and the shown result.
- **Privacy:** uploads exist only in memory for the running session. Nothing is written to disk (the only disk read is the optional synthetic dataset for the demo), nothing is logged, no external service, API, database or login is used. Extracted text appears only on screen (first 600 characters per file in a collapsed check) and in the per-candidate evidence snippets. The CSV contains ids, scores, skill names and warnings but no resume text; file names that begin with `=`, `+`, `-`, `@` are prefixed with an apostrophe so spreadsheets do not run them as formulas.
- **CSV:** one file per method with clear columns. Combined: `method, rank, candidate_id, status, combined_matching_index, semantic_cosine_raw, tfidf_cosine, required_skill_coverage, required_skills_total, matched_required_skills, missing_required_skills, matched_preferred_skills, warnings`. TF-IDF: `... tfidf_cosine, top_shared_terms ...`. Semantic: `... semantic_cosine_raw ...`. Components that were not calculated are absent for that method; an unavailable coverage is a blank cell, never 0 or 1; excluded files follow the ranked rows with an `excluded_not_scored` / `excluded_duplicate` status, no rank and no scores.
- **Verification done:** automated tests (see EXPERIMENT_RESULTS.md) including all three methods through the interface with the REAL model; the server was also started and loaded in a real browser (page rendered, demo job description filled and parsed into required / preferred skills, the missing-upload error shown). I could not upload PDFs through that browser tool, so file upload in a real browser is covered by the AppTest file-uploader tests only.
- **Known limitations:** inherits every Phase 8 limitation (dictionary blind to paraphrase and negation, coverage counts mentions, "A or B" reads as both, documents just under 254 tokens embedded whole); no OCR; duplicate detection is by identical file bytes only; Streamlit holds uploads in server memory, so use it on a machine you control; the app is for local use and has not been deployed.
