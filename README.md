# AI-Powered Resume Screening and Job Matching System Using NLP

A student NLP project. A recruiter pastes a job description and uploads several PDF resumes; the app
extracts the text, finds skills with a dictionary, scores every resume with three methods (TF-IDF,
pretrained sentence embeddings, and a combined index) and shows a ranked table with the evidence behind
each number. It is **decision support for a human reviewer**, not an automated hiring tool.

> **Read this first.** Scores are text-matching values, not probabilities of being hired and not verified
> competence. The only evaluation is a small **synthetic** one (5 invented jobs, 46 invented resumes), so
> nothing here shows how the system would perform on real recruitment data.

## Main features
- PDF text extraction (PyMuPDF) with explicit handling of empty, corrupted, password-protected, scanned
  (image-only), oversized and duplicate files. A bad file never stops the others and is never silently
  treated as an empty resume.
- Transparent, dictionary-based skill extraction with aliases (for example `sklearn` = `scikit-learn`) and
  required / preferred skills read from the job description.
- Three ranking methods you can switch between: TF-IDF baseline, semantic matching, combined ranking (default).
- Per-candidate details: matched and missing required skills, evidence snippets, warnings.
- CSV export, a built-in synthetic demo, and a cache that never mixes up different inputs.

## Architecture and workflow
```
PDF bytes -> pdf_parser -> preprocessing -> skill_extractor ----------------------+
                               |                                                  v
                               +-> tfidf_matcher (pairwise TF-IDF) --> ranker (combined index) -> app_logic -> app.py
                               +-> semantic_matcher (MiniLM, chunking) ----^         (table, details, CSV)
```
| File | Role |
|---|---|
| `src/pdf_parser.py` | PyMuPDF extraction, status per file, unique ids, duplicate detection by file hash |
| `src/preprocessing.py` | one cleanup step shared by three views (skills, TF-IDF, embeddings) |
| `src/skill_extractor.py`, `data/skill_dictionary.json` | rule-based skill matcher (editable JSON dictionary) |
| `src/tfidf_matcher.py` | TF-IDF + cosine; in the app and evaluation the IDF is fitted per job/resume pair |
| `src/semantic_matcher.py` | `sentence-transformers/all-MiniLM-L6-v2` (pretrained, used as published), chunking for the 256-token limit |
| `src/ranker.py` | combined index, required-skill coverage, ranking |
| `src/app_logic.py`, `app.py` | the three methods behind the interface, table, CSV, Streamlit page |
| `src/evaluate.py`, `data/evaluation/`, `artifacts/` | synthetic evaluation set, labels, metrics, saved results |
| `tests/` | pytest suite |
| `PROJECT_LOG.md`, `EXPERIMENT_RESULTS.md` | every design decision and every measured result |

Nothing is trained in this project: TF-IDF *fitting* only counts words, and the embedding model is a
pretrained model used as published (not fine-tuned by us). There is no LLM, API, database or login.

## Prerequisites
- Windows 10/11 with PowerShell. Everything was developed and tested on Windows 11; other systems are untested.
- Python 3.12 (tested with 3.12.10; other versions are untested).
- About 1.5 GB of disk for the virtual environment (measured: 1.48 GB) and about 90 MB for the language model
  (measured: 87 MB in the Hugging Face cache).
- Internet access for the first install and the first model download only. No GPU is needed.

## Setup (Windows PowerShell)
```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements-lock.txt     # exact tested versions (or: pip install -r requirements.txt)
```
If PowerShell blocks the activation script: `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.
The first semantic run downloads the model (about 90 MB) from Hugging Face; afterwards it is read from the
local cache. Loading takes about a minute on the development machine.

## Run the application
```powershell
streamlit run app.py
```
It opens at http://localhost:8501 and is restricted to `localhost` by `.streamlit/config.toml`
(upload limit 25 MB per file, Streamlit usage statistics off).

To avoid any contact with Hugging Face after the model has been downloaded once:
```powershell
$env:HF_HUB_OFFLINE = "1"; streamlit run app.py
```

## Using the app
1. Paste a job description (or pick a **Synthetic demo** scenario in the sidebar and press *Fill in this job
   description*). Headings such as `Requirements:` and `Nice to have:` let the app separate required from
   preferred skills; without them every detected skill counts as required and the app warns that the split is uncertain.
2. Upload PDF resumes (the sidebar can download the synthetic demo resumes as a ZIP; `data/sample_resumes/`
   has the same files plus edge cases such as a scanned, a password-protected and a corrupted PDF).
3. Choose a method in the sidebar and press **Rank candidates**.
4. Read the table, open a candidate's details, and download the CSV.

| Method | What it does | Columns |
|---|---|---|
| **Combined ranking** (default) | weighted index of the three components below | Combined matching index, semantic, TF-IDF, required-skill coverage |
| **TF-IDF baseline** | word-overlap cosine, IDF fitted on the job description and that one resume | TF-IDF similarity |
| **Semantic matching** | sentence-embedding cosine, long texts split into overlapping chunks | Semantic similarity (raw cosine) |

Skill coverage is a **score component, not a fourth selectable method**: the app offers TF-IDF, semantic and
combined. To look at candidates by coverage, run *Combined ranking* and click the "Required-skill coverage" column
header to sort. Ranking by coverage alone was evaluated only as an exploratory ablation (`X1_skills_only` in
`EXPERIMENT_RESULTS.md`).

## Score components
- **TF-IDF similarity (cosine, 0 to 1):** how much weighted vocabulary the resume shares with the job description.
  Blind to meaning: "sklearn" and "scikit-learn" are different words to it.
- **Semantic similarity (raw cosine, -1 to 1):** closeness of the two texts in the pretrained model's embedding
  space. It reflects topic, not whether the person did the work, and ignores negation.
- **Required-skill coverage (0 to 1):** matched required skills / required skills, using unique canonical skills
  from the dictionary. It counts mentions, not use, and is blank (never 0 or 1) when the job description has no
  identifiable required skills.
- **Combined matching index:** `0.50 x max(0, semantic) + 0.20 x TF-IDF + 0.30 x coverage`. The weights are
  initial design choices, not optimised and not tuned on any data. If coverage is unavailable the other two
  weights are renormalised, and the app says so. The index only orders candidates; it is not a probability or a percentage.

**Why coverage dominates the combined index on the evaluation set (measured, descriptive).** The three terms are
added without rescaling, so a term influences the ordering roughly in proportion to weight x spread. Over the 46
synthetic judgments the standard deviations are 0.346 (coverage), 0.089 (semantic) and 0.051 (TF-IDF). Skill coverage
swings from 0 to 1, while semantic cosines sit in a narrow band (0.35 to 0.87). Of the variance of the combined index,
about 75% comes from the coverage term, 20% from semantic and 5% from TF-IDF; the index correlates r = 0.93 with
coverage and 0.59 with semantic. So the combined ranking behaves mostly like a skill-dictionary ranking. This is a
property of this data and of weights fixed in advance, not a reason to change them, and it is why the combined index
inherits the dictionary's blind spots (keyword lists, negation, paraphrase).

## CSV export
The *Download ranking as CSV* button exports the ranking of the method that was run (`ranking_combined.csv`,
`ranking_tfidf.csv`, `ranking_semantic.csv`). UTF-8, one row per candidate, best first, then the excluded files.
- Combined: `method, rank, candidate_id, status, combined_matching_index, semantic_cosine_raw, tfidf_cosine,
  required_skill_coverage, required_skills_total, matched_required_skills, missing_required_skills,
  matched_preferred_skills, warnings`.
- TF-IDF: `method, rank, candidate_id, status, tfidf_cosine, top_shared_terms, warnings`.
- Semantic: `method, rank, candidate_id, status, semantic_cosine_raw, warnings`.
- A component that was not calculated has no column. An unavailable value is an empty cell, never 0 or 1.
- `status` is `ranked`, `no_usable_text`, `excluded_not_scored` or `excluded_duplicate`; excluded files have no rank
  and no scores, only the reason in `warnings`.
- Candidate ids starting with `=`, `+`, `-` or `@` get a leading apostrophe against spreadsheet formula injection.
- The CSV never contains resume text.

## Synthetic evaluation (what was measured)
5 synthetic job descriptions, 46 synthetic resumes, graded labels written from a rubric before any method was run
(`data/evaluation/`). Relevant = label 2 or 3. K = 3, macro average over the 5 jobs.

| Method | Precision@3 | Recall@3 | MRR | nDCG@3 |
|---|---:|---:|---:|---:|
| TF-IDF | 0.467 | 0.300 | 0.567 | 0.461 |
| Semantic | 0.600 | 0.390 | 1.000 | 0.651 |
| Combined | 0.600 | 0.390 | 0.900 | 0.654 |

**Honest reading:** the combined index scored higher than TF-IDF alone on this set, but it did **not clearly
outperform semantic matching alone** (equal Precision@3 and Recall@3, nDCG differs by 0.003, MRR is lower). Per job
the combined index was better on two jobs and worse on three on nDCG. These three-decimal numbers come from 5 jobs
and are not evidence of statistically significant differences. Keyword-heavy resumes fooled TF-IDF, negation and
"recruiter describes the role" resumes fooled the semantic score, and skill coverage rewarded keyword lists and
could not see paraphrased experience. Full tables, failure cases and exploratory ablations: `EXPERIMENT_RESULTS.md`.
Reproduce with `python -m src.evaluate` (results were reproduced exactly in Phase 10).

### Evaluation limitations
Same author wrote the system, the resumes and the labels; one annotator, no agreement measured; labels are
subjective; only 2 of 46 resumes exceed the model's token limit; resumes are short, clean and invented. Skill-extraction
precision 1.000 / recall 0.989 on 17 annotated resumes is mention-level detection of dictionary words written by
the same author and must not be read as real-world accuracy.

## Known limitations
- **No OCR.** Scanned PDFs are detected and reported as needing OCR, not read.
- **Dictionary-based skill extraction.** Not a trained NER model: unlisted skills and paraphrases are invisible,
  ambiguous words (Go, R, React...) rely on rules, and "PyTorch or TensorFlow" is read as both.
- **No negation or role understanding.** "I have not used Python" and "I recruit Python developers" still
  match Python; the semantic model has the same blind spot.
- **English only.** Non-Latin text gives TF-IDF no words and the embedding model is English-oriented.
- **One chunk can decide the semantic score** for a job description that fits one chunk, and a document just under the
  254-token limit is embedded whole (a relevant tail can be diluted).
- **Chunk size vs training length:** the model card says the model was trained with 128-token sequences, while chunks here are up to 200 tokens (within its 256-token input limit); the effect was not evaluated.
- **Duplicate detection** matches identical file bytes only.
- **Limited evaluation:** synthetic, small, single-author (above).

## Responsible use and privacy
- Use it only on resumes you have permission to process, and have a person review every candidate. Do not use scores
  as the sole basis for rejecting anyone; resume wording and formatting can affect scores unrelated to ability.
- Uploads are held in memory for the running session (cached at most 8 inputs per browser session for up to an hour)
  and, by code inspection and tests, are not written to disk by this project's code and not logged. "Clear cached data
  now" in the sidebar empties the caches. Streamlit keeps uploads in server memory, so run the app on a machine you control.
- This project's code imports no networking library and sends resume text to no service. The sentence-transformers
  library contacts Hugging Face when the model is loaded (to download it the first time and to check for updates;
  no resume text is sent); `HF_HUB_OFFLINE=1` after the first download prevents that, and the model loads from the
  local cache (checked by hand in Phase 10; not part of the automated suite).
- The CSV contains ids, scores, skill names and warnings, never resume text. File names starting with `=`, `+`, `-`
  or `@` are prefixed with an apostrophe so spreadsheets do not run them as formulas. The CSV is UTF-8; if Excel garbles
  non-English file names, import it with *Data > From Text/CSV* and choose UTF-8.
- Do not put real resumes in this repository (`.gitignore` excludes `data/private/` and `data/uploads/`).

## Troubleshooting
| Symptom | Cause and fix |
|---|---|
| `Activate.ps1 cannot be loaded` | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`, then activate again. |
| `ModuleNotFoundError: No module named 'src'` | Run commands from the project folder (the one containing `app.py`). |
| First semantic run is very slow | It loads the language model (about a minute on the development machine, which keeps the project in OneDrive). Later runs reuse it. |
| Red message "The language model could not be loaded" | The model is not on this computer yet and there is no internet. Connect once and run any semantic or combined ranking; it is then cached. |
| Want to run without contacting Hugging Face | After one successful run: `$env:HF_HUB_OFFLINE = "1"; streamlit run app.py`. If the model was never downloaded, offline mode fails with the message above. The cache is normally `%USERPROFILE%\.cache\huggingface\hub`. |
| `Port 8501 is already in use` | Another instance is running. Stop it, or use `streamlit run app.py --server.port 8502`. |
| A PDF shows "Probably scanned: OCR needed" | It is an image without a text layer. OCR is not implemented; use a text PDF. |
| A PDF shows "Password-protected" / "Unreadable or corrupted" / "Too large" | Remove the password, re-save the PDF, or reduce it. The parser refuses files over 10 MB; Streamlit refuses over 25 MB. |
| A resume is "No usable text" | The PDF has under 100 characters of readable text, or none. Open it and check. |
| TF-IDF says the job description has no usable words | It contains only stop words, punctuation or numbers; add the role's requirements. |
| Coverage column is empty | The job description has no identifiable required skills (see the warning shown under the job description). |
| Everything is slow, or OneDrive reports file locks | The project is inside OneDrive, which syncs `.venv`. Exclude `.venv` from sync or move the project elsewhere (then recreate the virtual environment). |
| Excel garbles non-English file names in the CSV | Import via *Data > From Text/CSV* and choose UTF-8. |
| Long console tracebacks mentioning `torchvision` while the app runs | Streamlit's file watcher scans optional modules and prints harmless errors (315 in one captured run); no result is affected. Ignore them. (Streamlit's `--server.fileWatcherType none` option should silence them, but it was not tried here.) |
| Tests take 3 to 4 minutes | Normal here (real model plus OneDrive). Full runs: 389 passed in 207 s (Phase 10) and 389 passed in 192 s (Phase 13, 2026-10-24). |

python -m pytest -q

## References (checked against their publisher or official pages)
- N. Reimers and I. Gurevych, "Sentence-BERT: Sentence Embeddings using Siamese BERT-Networks", EMNLP-IJCNLP 2019,
  DOI 10.18653/v1/D19-1410 (https://aclanthology.org/D19-1410). Background for sentence embeddings compared by cosine.
- W. Wang, F. Wei, L. Dong, H. Bao, N. Yang, M. Zhou, "MiniLM: Deep Self-Attention Distillation for Task-Agnostic
  Compression of Pre-Trained Transformers", arXiv:2002.10957 (https://arxiv.org/abs/2002.10957). The compression
  method behind the small base model family; `all-MiniLM-L6-v2` is a model published through the sentence-transformers
  project, used here exactly as published. The details of how it was fine-tuned (about 1 billion sentence pairs, contrastive
  objective, 384 dimensions) come from model-card mirrors found by web search, not from the official card; the 384
  dimensions and the 256-token limit were also measured on this machine.
- scikit-learn documentation of `TfidfTransformer`/`TfidfVectorizer` (https://scikit-learn.org/stable/modules/generated/sklearn.feature_extraction.text.TfidfTransformer.html):
  the smoothed IDF `ln((1+n)/(1+df)) + 1` and `sublinear_tf` (`1 + ln(tf)`), both also checked numerically in the tests.

## Manual check with real PDFs
1. `streamlit run app.py`, open http://localhost:8501.
2. Sidebar: pick *Backend Software Developer*, press *Fill in this job description*; confirm Python, SQL,
   PostgreSQL, Docker, REST API are required and Kubernetes, AWS, CI/CD preferred.
3. Upload the ten PDFs in `data/sample_resumes/realistic_backend_set/` and paste its `job_description.txt`. Confirm all ten are
   listed as readable and ranked. (The earlier `backend_demo/` and `edge_cases/` sample folders were deleted at the user's request; to
   try bad files, upload your own blank, password-protected or corrupted PDF and check the status table.)
